# Основы архитектуры ПО
## Тема 1. Оптимизация и рефакторинг кода на Java

### Задача
Я переработал класс OrderProcessor из приложения к заданию.
Для confirmed сохранены три действия: подтверждение, обновление склада,
формирование счета. Для shipped сохранено обновление доставки.
Другие ненулевые статусы пропускаются. Порядок заказов и операций сохранен.
Как и в исходнике, операции демонстрируются сообщениями в консоли:
реальные письма, склад и счета в проекте не реализованы.

В предоставленном PDF метод generateInvoice обрывается.
Его предполагаемое завершение восстановлено по аналогии:
вывод "Generating invoice for order #" и номера заказа.

### Анализ исходника
Один класс выбирал сценарий и выполнял все операции.
Дублировались форматирование сообщения и вывод номера заказа.
Цикл и выбор действий находились в одном методе.
Зависимости нельзя было заменить без изменения OrderProcessor.
Названия sendConfirmationEmail и updateInventory уже достаточно понятны,
поэтому переименование ради переименования не требуется.
Неиспользуемых импортов в показанном фрагменте не обнаружено.

### Этапы изменений
1. Выделил повторяющийся вывод в OrderLogger.log.
2. Разделил обход списка processOrders и обработку одного заказа processOrder.
3. Вынес четыре операции в отдельные классы с общим интерфейсом OrderAction.
4. Передал правила обработки через конструктор. Конкретные операции связываются в Main.
5. Добавил JavaDoc к классам, методам и конструкторам.
6. Проверил сборку, запуск и шесть сценариев итоговой версии.

### SOLID
- S: Order хранит данные, OrderLogger форматирует вывод, классы операций
  отвечают за отдельные действия, OrderProcessor управляет выполнением.
- O: новый статус и действия добавляются настройкой Map в Main;
  код OrderProcessor менять не требуется.
- L: реализации OrderAction используются через единый контракт execute.
- I: интерфейс содержит только один необходимый метод.
- D: OrderProcessor зависит от абстракции OrderAction; конкретные реализации
  передаются извне. Классы консольных операций используют конкретный OrderLogger:
  для небольшого учебного примера дополнительная абстракция вывода не вводилась.

### Оптимизация и ограничения
Главный результат — читаемость, устранение дублирования и расширяемость.
Алгоритм по-прежнему линейный по количеству заказов при фиксированном
числе действий на заказ. Ускорение измерениями не заявляется.
Поиск набора действий выполняется через HashMap; для двух статусов это
архитектурное решение, а не доказанный выигрыш производительности.
Данные заказа неизменяемы, настройки обработчика защитно копируются.
Null-заказы и null-статусы не поддерживаются, как и в исходном примере.
Повторный запуск снова выполняет действия, как исходная программа.

### Запуск в IntelliJ IDEA
1. Создать Java-проект OrderRefactoring с JDK 17 или новее.
2. Скопировать все файлы из папки src архива в src проекта.
3. Открыть Main.java и запустить метод main.
4. Для проверок скопировать OrderProcessorTest.java из tests в src проекта
   и запустить его main. Внешние библиотеки не нужны.

### Запуск через терминал
Из корневой папки проекта, при наличии JDK 17:

```sh
javac -encoding UTF-8 -Xlint:all -d out src/main/java/*.java src/test/java/*.java
java -cp out Main
java -cp out OrderProcessorTest
javadoc -encoding UTF-8 -docencoding UTF-8 -private -d docs src/main/java/*.java
```

Ожидаемый вывод Main:

```text
Sending confirmation email for order #1
Updating inventory for order #1
Generating invoice for order #1
Updating shipping status for order #2
```

### Проверки
Автоматические проверки итоговой версии:
1. confirmed: ровно три сообщения в исходном порядке.
2. shipped: ровно одно сообщение о доставке.
3. pending: нет сообщений.
4. Пустой список: нет сообщений.
5. Смешанный список: сохранены порядок заказов и порядок операций.
6. Новый cancelled: действие выполняется без изменения OrderProcessor.

Фактический результат: PASS: 6 checks.
Сборка и запуск проверены на OpenJDK 17.
Проверки промежуточных версий отдельно не зафиксированы;
перед сдачей рекомендуется пройти этапы в отдельных коммитах
и повторить соответствующие проверки на каждом этапе.
